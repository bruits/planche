# Contributing Guidelines

## Philosophy

Planche is a fast, open-source board to gather reference images. You drop in pictures from anywhere, lay them out on a canvas, and annotate them with notes, arrows, shapes, drawings, and comments. A board is a folder of plain files that belongs to its user: it moves between machines without loss, diffs well in Git, and needs no account.

The app stays small on purpose. Its core covers what a reference board needs, including simple non-destructive edits (crop, rotation, flip, and greyscale), and anything beyond goes into plugins. An optional, paid cloud may add live collaboration and sync one day, but the app works fully without it.

Three priorities guide the trade-offs. Performance: a board of hundreds of large photos opens quickly and stays smooth to pan and zoom on ordinary hardware, and the rendering choices in the [foundation](./docs/technical/foundation.md#rendering) follow from this. Agentic workflows: an embedded MCP server lets agents read and edit a board as people do, and plain files let them work on it like any other file in a repository. Every platform: the browser, Windows, macOS, and Linux first, then iOS and Android, all running the same Rust core behind thin shells. The core does no I/O, so the same code builds natively and for the browser.

## Quality Guidelines

- Prefer self-documenting code first, with expressive names and straightforward logic. Comments should explain *why* (intent, invariants, trade-offs), not *how*, and are never used as decorations or separators.
- Variable and function names should be clear and descriptive, not cryptic abbreviations. Avoid hidden state and side effects.
- Explicit `use` imports for standard library types (e.g. `use std::collections::BTreeMap;`).
- Prefer `?` propagation when possible, and reserve `.expect()`/`.unwrap()` for cases where failure is a programmer bug.
- For errors, use typed error enums in library crates (derived with `thiserror`), with a per-crate `pub type Result<T>` alias. Add context at the boundary (the shells) rather than deep in the core, and keep library error messages concise.
- Keep the web app's TypeScript `strict`-clean: honour the null checks rather than casting them away with `!` or `as`, and never use `any`. Absence is a value, not a failure: return `undefined` and consume it with `?.` and `??`, reserve `!` for what would be a programmer bug, and throw an `Error` whose message the user or the agent reads for a failure.
- Every promise is awaited, returned, or marked `void` with its failure reported (e.g. through `report` in `main.ts`), so that a failure reaches the user rather than the console.
- Import types with `import type`, and the core as a namespace (`import * as core`), so that its calls read as the core's. oxfmt formats the web app and oxlint lints it, so `just fmt` and `just lint` settle style rather than review.
- We deeply value idiomatic, easy-to-maintain Rust and TypeScript code. Avoid code duplication when possible. Prefer clarity over cleverness, and small focused functions over dark magic.
- Tests should assert observable behaviour, not internal implementation details. Keep tests deterministic and independent of global state.
- The web app's tests sit next to their module (e.g. `save.test.ts`) and run with Vitest, in Node unless they need the DOM, then in happy-dom. They drive the real core, never a mock of it, and fake only what lies around the unit under test: the browser, the shell, timers, and the collaborators it is handed, such as a save's store or an editor's hooks. New web behaviour ships with tests, and existing behaviour is covered when touched.
- The web app's modules do no work on the page when imported (no DOM lookup, page listener, or top-level `await`), so that tests can import them. Only `main.ts`, which wires them together, and `platform.ts` and `browser.ts`, which set up the shell the page runs in, do, so a test that reaches them runs in happy-dom.
- The core builds for `wasm32-unknown-unknown`. `board` and `format` do no I/O and read no clock or randomness source: the caller passes them in (e.g. the bits of a new `ElementId`).
- Board files are deterministic. The same board always writes the same bytes, and an edit to one element rewrites one file, so nothing on that path iterates a `HashMap`.

## Getting Started

Planche is a Rust monorepo using [Cargo workspaces](https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html). The core needs [rustup](https://rustup.rs/), which installs the toolchain and the WASM target pinned in `rust-toolchain.toml`, and [just](https://github.com/casey/just) for the recipes listed in [AGENTS.md](./AGENTS.md). The app also needs [Node.js](https://nodejs.org/) and [pnpm](https://pnpm.io/), then `just setup`, which also installs its formatter, linter, and test runner, Python 3 for `just serve`, and on Linux the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/). On Windows, `just` runs its recipes with the `sh` of [Git for Windows](https://gitforwindows.org/).

The app is one web app in `web/`, in TypeScript without a framework, which runs the core as WASM on every platform: in a browser, and in the desktop shell's webview. Dependencies only point inward: `bindings` → `format` → `board`, and `desktop` → `folder` and `mcp`, which know nothing of boards, and `format`, for which of a board's files the web app may write. The crates live in `crates/`:

### board

The board as plain data: elements (images, notes, sticky notes, shapes, arrows, lines, pen strokes, comments, and groups), their geometry, their style (colours from a palette that each theme draws its own way, or of their own, stroke weights, dashes, arrowheads, fills, the face and alignment of their text, and opacities, each element taking its own parts of it, and a part chosen as it comes written as nothing), their stacking, and non-destructive image edits, and what shows behind them, plain or a grid, whose lines what moves near them snaps to. A pen stroke holds its points within its frame, from 0 to 1 across and down, to a hundred thousandth, so that moving, scaling, or turning it leaves them as they are, and it is hit, touched, and erased along its line. The ends of arrows and lines stick to the element they land on, and notes, sticky notes, shapes, and comments to the image, note, sticky note, or shape filled or holding text they are set down on whole. What sticks follows its element, keeping to the same pixel of an image however it is moved, scaled, turned, cropped, or flipped, and to its size as a side of the element is stretched. Element ids are drawn by the caller, assets are named by the SHA-256 digest of their bytes, and an SVG's natural size is read from its bytes by one rule, where engines disagree. Whether an image moves, and how many times it plays, is read from its bytes too, as browsers play it, and so is whether it is a video, from as little of their start as tells, so that shells copy few files whole into the core. An image may also keep where it came from, the name of the file it was added from, which shells keep without its path, and a caption. Images pack into rows by that name, by size, around the colour wheel from the mean colours the shell reads, or at random from a seed it draws, size alike by height or width, and crop, as a rectangle or an ellipse, with each pixel they still show staying where it was. Elements line up on a side or the middle of their extent, or, three or more, space out evenly between the first and last, each whole with what its groups hold, and what sticks to another of them follows it. Each element stacks among its siblings by a fractional z-index, so restacking one rewrites one file, and a board that Git merged into a group cycle, or with something stuck to an element another branch deleted, or to what sticks to it, is repaired on read. Edits go through an `Editor`, whose undo history keeps every touched element, and the background, as it was, in memory only. A flip, a scale, a turn, and a move go as one, which sets down what it moves wherever it lands, for users and agents alike, and an arrow's or a line's end lands as the core says, locked at 45° or pulled by the grid. What each element draws, as the renderer takes it, is compiled here too: the part of its asset an image shows, flipped within its crop, or its frame crossed out while its asset cannot show, an arrow's heads, a shape's outline with its fill, a pen stroke's points on the board, a sticky note's paper, and where a text stacks, which the web app lays out. A comment draws nothing, so the elements' extent, which views and agents frame, and what an area touches, take the point it is pinned at.

### format

The board as a folder of files, keyed by path, and back: a `board.json` manifest holding the format version and the background, left out when plain, one JSON file per element in `elements/`, image bytes in `assets/`, and a `.gitattributes`, written when the board is created, that keeps Git from converting line endings and sends assets to Git LFS. The same files also travel as a single ZIP file, which the core reads and writes without I/O, so that a shell moves it a slice at a time. `samples/demo/` holds a board to try the shells on, and `samples/demo.zip` its ZIP file, which every platform must write byte for byte. Assets never change once named, so the caller writes each one once and checks it against its digest when loading it, which catches a board cloned without Git LFS. A save writes only the files whose bytes changed since the app read or wrote them, and deletes only the element files it knew, see [saving](./docs/technical/saving.md). It implements the file format decided in the [foundation](./docs/technical/foundation.md): until the first release, it can change freely; from then on, any change to its shape bumps `FORMAT_VERSION`, and earlier versions are migrated on read.

### bindings

The core for the web app, through [wasm-bindgen](https://github.com/wasm-bindgen/wasm-bindgen): an `Editor` holds the board being edited, elements and what they draw cross as JSON, the latter kept by the web app for each element until an edit touches it, typed by the TypeScript declarations that `board` writes into its bindings as they build, ids as strings, and files as paths and bytes, in slices when named as an asset or checksummed for a ZIP file, as the core's memory never shrinks. Its CLI must match the crate's version in `Cargo.lock`, which `just setup` installs.

### desktop

The desktop shell, on [Tauri 2](https://v2.tauri.app/): a window around the web app, and the file system that a browser lacks, limited, for the web app, to the folders and ZIP files the user picks and the files dropped on it, where it writes only a board's files, deletes only its element files, and writes a file picked to export to once complete. It keeps the session's board and the last board's path in the app's data folder, and lets the web app write what waits before a window closes. The webview takes dropped files itself, but not on Linux, where WebKitGTK hides them from pages, so the shell takes them there. It keeps its window above other apps' windows when asked, where the system lets it, which Wayland does not. It hides its title bar when asked, and the web app stands in for it. The click that brings its window forward also acts on the board, on macOS as elsewhere, since a board floats over other apps. It opens an image's source in the system's browser, when a web address, as the webview opens no window. On macOS, it tells the web app what each key types without a modifier in the layout in use, which the webview does not, so that ⌥ shortcuts follow the letter printed on a key. Once the user turns agent access on, it passes agents' calls on to the web app, and reads the image files they add for them, and run as `desktop mcp`, it is the gateway an agent's client spawns. It is the Tauri track from the [foundation](./docs/technical/foundation.md), under test in the prototype.

### renderer

The renderer, on wgpu: images as textured quads, cut to an ellipse when cropped as one, the frames of animated ones, which it decodes itself, and of videos, which the host plays, SVGs and text from textures the web app rasterises, the strokes of arrows, lines, pen strokes, which see-through draw each pixel once however they cross themselves, and the outlines of shapes, dashed or not, and the fills of shapes and sticky notes, in their own colours and their elements' opacity, in one list back to front, as the core compiles it, over the grid, if any, on WebGPU or WebGL2, for the web only so far. It also draws, for agents, and for the selection exported or copied as a PNG, a part of the board onto a texture of its own, which it reads back, with the window's canvas, camera, and textures left as they are. See the [foundation](./docs/technical/foundation.md#rendering).

### folder

A folder on disk as the desktop shell reads and writes it: paths with `/` between segments, atomic writes, removals, the stamps that tell another program's changes, and nothing that leads out of it, neither links nor dot folders such as `.git/`. A single picked file, such as a ZIP file, is read in ranges and written in parts, just as atomically. It needs no Tauri, so its tests run on every platform.

### mcp

How agents read and edit the board open in the desktop app, over [MCP](https://modelcontextprotocol.io/). An agent's client spawns the gateway, which passes bytes between its standard streams and the app, over a port of this machine only, once each side proved itself with a secret. Both find each other, and the secrets, through a file only the user can read, which exists while agent access is on. The app answers each tool call by asking the web app, which holds the board. It needs no Tauri, so its tests run on every platform, one of which checks that `web/src/arguments.ts` declares the arguments of its tools as it takes them. Each edit waits for the user to finish a drag, a text, or a crop, then undoes in one step, and saves as the user's edits do. It is the MCP track from the [foundation](./docs/technical/foundation.md).
