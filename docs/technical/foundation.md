# Technical foundation

What is decided, what is still being explored, and why. A track becomes a decision once the prototype has measured it; decisions are rules for the code, and nothing is frozen until a release.

## Decided

- **Stack.** Mostly Rust, with a thin presentation layer: one web app in TypeScript, without a framework, runs the Rust core as WASM in the browser and in the desktop shell's webview.
- **Platforms.** The browser, Windows, macOS, and Linux first. iOS and Android come later, but the design must not rule them out.
- **File format.** A folder of deterministic JSON files, one per element, with images named by their SHA-256 digest (`crates/format`). A single-file export is a ZIP of that folder, holding the board's files and the images it draws: stored rather than deflated, since images are compressed already, dated 1980-01-01, and never ZIP64, so that the same board gives the same bytes and a shell reads an image straight out of it. A ZIP file that another tool compressed is refused rather than inflated. Images need Git LFS. SQLite (as in BeeRef) was rejected because Git cannot merge it, and a single JSON with base64 images (as in `.excalidraw`) because it is heavy and its diffs are useless. JSON Canvas is too poor as a native format, but fits import and export. How a board saves itself into it is in [saving](./saving.md).
- **Licence.** MIT or Apache-2.0 for the client and the format. The sync server, if there is one, will be AGPL.

### Rendering

wgpu, compiled to WASM (`crates/renderer`) and driven by the web app, on WebGPU where the webview has it and on WebGL2 otherwise. A bake-off against DOM, Canvas2D, raw WebGL2, PixiJS, and Three.js (its bench and results are at commit `ac764a9`) found that the renderer is not the bottleneck: every GPU candidate held 60 fps with 300 photos. wgpu is the WebGPU API in Rust, drew at the lowest cost on WebGPU, and can later run natively, without a webview. It costs a breaking release about every quarter, and on WebGL2 about six times the CPU time of raw WebGL2: 1.3 ms against 0.1 ms per frame for 300 images.

- Everything a board holds draws on the GPU, in one list back to front, so that it stacks as its z-indices say: images as textured quads, strokes, fills, and the edge of an image cropped as an ellipse as quads whose fragments measure how far they are from the shape in device pixels, which smooths edges without multisampling, and text as a texture of its coverage, tinted with its colour. The DOM only holds the field that text is written in, and comments, as pins at one size on screen whatever the zoom, above everything the board draws.
- The core compiles what each element draws from that element alone and the assets that cannot show, and the web app keeps each element's items until an edit touches it or those assets change. Compiling the whole board at each step of a drag would cross the WASM boundary as JSON in 0.8 ms at 500 elements and 4.8 ms at 3000, against 0.08 ms for the 50 elements a drag moves, in Node on a release build (`just bench`).
- The grid draws first, over the whole viewport, its fragments measuring in device pixels how far they are from the nearest line or dot, put on whole pixels so that it stays sharp. The core picks its level for the zoom, which snapping uses too, and the app hands over where it starts less whole cells, worked out in doubles, as floats would blur its lines far from the origin.
- Text is laid out and rasterised by the host, which holds the font: Inter, bundled, so that it wraps alike wherever it opens. It breaks where the field it is written in breaks (`white-space: pre-wrap`), which the app follows by rule rather than by asking the engine: the line counts matched in Chromium and WKWebView but for CJK, which Inter lacks, tabs, and words too long for a line. WebKitGTK is not measured yet.
- Each text has a texture of its own, at the zoom it shows at rounded up to a power of two, at most 2048 px a side, and at 8 px per font size once out of view. A texture replaced is destroyed (`Texture::destroy`), since dropping one frees nothing on WebGPU. Zooming in and out over the demo board, and editing and undoing its text, over and over, left texture memory where it started, on WebGPU and WebGL2 in Chromium.
- SVGs are rasterised by the host too, on the main thread, through an `<img>`, since `createImageBitmap` refuses an SVG's bytes, and from a `data:` URL, since a `blob:` one taints the canvas once the SVG holds a `foreignObject`. Engines disagree on the size of an SVG sized by its `viewBox` or by percentages, and on one with neither, which Chromium lays out at whatever size it is drawn and WKWebView at 300 by 150, stretched, so the core gives each SVG one natural size: its absolute `width` and `height`, what is missing from its `viewBox`'s ratio, its `viewBox`'s own size when neither is absolute, and CSS's 300 by 150 for what is still missing. The app draws a copy whose root holds that size, as text is drawn: at the zoom it shows at rounded up to a power of two, at most 2048 px a side, and at 256 px a side once out of view. The asset keeps its bytes, as an `<img>` runs no script and loads nothing. This held in Chromium and WKWebView; WebKitGTK is not measured yet.
- Animated GIFs, PNGs, and WebPs are decoded by the renderer, a frame at a time, with `image` (its `gif`, `png`, and `webp` decoders), since not every webview hands their frames over: an animated `<img>` draws its first frame in Chromium and WKWebView, and WKWebView and WebKitGTK lack `ImageDecoder`, which WebKit ships only in Safari Technology Preview so far. The browser gives the first frame, and each one after goes straight onto the asset's texture, on the main thread, the most overdue first, none starting once a frame has spent 8 ms on them, and only while an image of the asset shows, so that memory follows what shows whatever its length. Their frames are not colour-managed, so an APNG with a colour profile, or in WKWebView a WebP with one, may shift from its first frame. Those past 2048 px a side, or turned or flipped by their metadata, stay still. The core reads from the bytes whether an image moves and how many times it plays through, as Chromium and WKWebView play it: a GIF once without a loop extension, and once more than it repeats with one. A frame asking for 10 ms or less shows for 100 ms. A frame decodes in 0.3 to 0.5 ms at 480 by 270 px and in 2.3 to 2.9 ms at 1000 px a side, and `image` adds 0.4 MB to the renderer's WASM. Playback held in Chromium; WKWebView and WebKitGTK are not measured yet.
- Videos, MP4, QuickTime, WebM, and Matroska where the platform plays it, which the core knows by the start of their bytes, play in a `<video>` the page never shows, from a `blob:` URL typed as the core says, since WKWebView refuses an untyped `isom` MP4 or QuickTime movie. The renderer copies each frame the host presents (`requestVideoFrameCallback`, or a new `currentTime` at each draw where it is missing) onto the asset's texture, which the browser made from its first frame at the video's own size, while it shows and plays, the 8 largest on screen at most, as decoders are few and Chromium allows 75 in a page. Where the user chooses so in the app, one the user did not play plays only while the pointer is on it, a preference the browser remembers apart from any board. A copy from a `<video>` that has no frame yet throws, which wgpu's WebGPU backend turns into a panic that kills the WASM module, so the renderer copies only once one has, and its `preload` is `auto` before its source: with `metadata`, the copy throws even once ready in Chromium, and WKWebView loads no frame until it plays. A detached `<video>` plays on in a visible page, in Chromium and WKWebView, and a hidden page pauses it in Chromium and presents about a frame a second in WKWebView, so the app stops them while hidden. `VideoFrame` from WebCodecs would need `web_sys_unstable_apis`, without which WebGL2 panics on it. The codecs are the platform's: WebKitGTK needs `gst-libav` for H.264, and HEVC may show nothing in WebView2 without failing. A video over 300 MB, or past 4096 px a side, is not added, and one a machine cannot play shows crossed out there. A video whose frames change size partway, as a browser's recording of a resized window may, stops on the last frame of its first size until the board opens again, as its texture keeps that size. A frame copied at 1080p or 4K took 1 to 2 ms in Chromium. What WKWebView does here was measured on test pages in a WKWebView on macOS 26, the app itself has played only in Chromium, and WebKitGTK is not measured yet.
- WebGL2 stays a first-class target: WebKitGTK, the Linux webview, has no WebGPU.
- Request the adapter's limits (`Limits::using_resolution`), since WebGL2's defaults cap textures at 2048 px.
- Uniform buffers are multiples of 16 bytes on WebGL2.
- Catch validation errors (`Device::on_uncaptured_error`) and hand them to the app: by default wgpu panics, which kills the WASM module.
- Read a render back through a buffer, as a surface cannot be copied from. WebGL2 maps it only when the device is polled, between turns of the event loop, so the app polls at each turn, which a hidden window still takes, where it would never get a frame. Its rows cross the WASM module's memory one at a time on their way to a JS array, as that memory never shrinks, and reading a WebGPU mapping as a Rust slice copies it whole. In Chromium, a render of 4096 by 4096 px grows the module by nothing on WebGPU, and on WebGL2 by the 67 MB of the emulated mapping that wgpu keeps in it, against 134 MB on both when read whole.
- Vello stays out for now: its GPU renderer is being rewritten, and its image atlas cannot hold many photos. It may come back if text or strokes outgrow the above.

### Image pipeline

The direction is decided, and only decoding, freeing what no image draws, and mipmaps in linear light are built so far, not the residency planner, levels of detail, tiles, or caches. The pipeline, not the renderer, sets performance: a 12 MP photo takes 48 MB once decoded, so what sits on the GPU must follow what is on screen, whatever the number of photos.

- **Decoding** happens in the browser, off the main thread, with `createImageBitmap` (resized, `imageOrientation: "from-image"`). It beat Rust in WASM, 65 ms against 83 ms for 12 MP, and is the same code in every webview. The formats are the platform's, so HEIC only on Apple platforms. Four images at a time are read, checked against their digest, decoded, and uploaded, the largest on screen first, and each shows once uploaded: a board of 100 photos of 12 MP shows its first in 0.2 s and all in 4.3 s, in Chromium on an Apple M5 Pro, where none showed before 4.9 s. An image this machine cannot decode or upload shows crossed out, as a video it cannot play does, while a missing asset, or one unlike its digest, keeps the board from opening, as saving it would fail. Once no image draws an asset, still, animated, video, or SVG, its texture is freed at the next frame no gesture holds, and an undo, a redo, or an agent's edit that brings it back reads, checks, and decodes it again the same way, about 60 ms a photo, its animation or video waiting for its texture; one that then fails shows crossed out alone, until the board opens again. 100 photos of 12 MP held 1.6 GB of textures, which deleting them freed and undoing read again, on WebGPU and WebGL2 in Chromium.
- **Residency** is planned by the Rust core, without I/O: from the camera and the visible images, it gives uploads and evictions within a memory budget. It keeps a coarse level of every image, never evicts what is on screen, and serves each image at its size on screen. No crate does this; `lru` or `quick_cache` can serve as parts.
- **Levels of detail** are whole images at halving sizes. Mipmaps are generated on the GPU, each level drawn from the one above, into `Rgba8UnormSrgb` textures, so that filtering happens in linear light, and images encode their colours back to sRGB as they draw, since the surface stays in sRGB values for the strokes, text, and grid, which blend as the page does. A black and white checkerboard zoomed out shows at 188 out of 255, where `Rgba8Unorm` mipmaps darkened it to 127, and colours at 1:1 stay as decoded, byte for byte, on WebGPU and WebGL2 in Chromium. Greyscale takes the luminance of the linear light.
- **Tiles** only past the texture limit, cut with a cropped `createImageBitmap`, since wgpu's WebGL2 backend only copies whole images.
- **Caches** of derived levels stay out of the board: the app's cache folder on desktop, OPFS on the web, keyed by the asset's digest.

Later, only if measurements call for it: native decoding on desktop, Rust decoders in WASM for more of what browsers lack (`jxl`, `moxcms`), GPU texture compression (WebGPU only), and rendering in a worker. Not viable today: WASM threads, which need nightly Rust and a cross-origin isolation that WKWebView may not grant under `tauri://`, and a HEIC or AVIF decoder in Rust under a permissive licence.

## Tracks

Current preferences, not decisions yet.

### Shell

Tauri 2 around the web app, with the system webview.

- **Limits:** WebKitGTK is slow on Linux, has no WebGPU, and may fall back to software WebGL without saying so. Tauri's Chromium runtime (CEF) is still an alpha. The clipboard handles only text on mobile. Transparent windows are buggy on every desktop platform.
- **Alternatives:** wgpu and winit without a webview, at the cost of handling text, IME, and accessibility ourselves; since the renderer is wgpu, this stays open if webviews fall short. Dioxus shares the webview limits, and Slint and Makepad fit this case less well.

### Sync

A Loro CRDT, whose movable tree maps well to groups. A Phoenix or Axum server, and S3 storage for images.

- **Limits:** Loro is young, and reconciling the CRDT with Git is ours to design. Loro needs randomness and a clock, so it must live outside `board` and `format`.
- **Alternatives:** Automerge 3, or Yjs/Yrs, the most proven but without a native movable tree.

### MCP

rmcp, the official SDK. On desktop, a stdio gateway, which every client can spawn, passing bytes to the app over a local port protected by a token, so that no page in a browser can reach it. On the web, a remote MCP through the cloud.

- **Limits:** WebMCP is only a draft, so nothing should depend on it. Image content is a prompt injection risk, and an agent that reads it may edit the board, which saves itself, so that only undo or Git takes an edit back. An agent may also add, and so see, any image file the user can read, even from a sandboxed client. Each edit waits for the user to finish a drag, a text, or a crop, as it would otherwise join it.

### Plugins

WebAssembly components described in WIT: wasmtime on desktop, jco in the browser.

- **Limits:** iOS has no JIT, so it needs the Pulley interpreter, about ten times slower.
- **Alternatives:** Extism, simpler to set up; a JavaScript sandbox, as Figma does; or Lua/Rhai.

## Main risk

Canvas performance in webviews, above all WebKitGTK on Linux and WebKit on iPad. The bake-off only ran in headless Chrome on an Apple M5 Pro. Safari and WKWebView, Firefox, WebView2, and WebKitGTK, on modest GPUs, are still to run, with the bench at `ac764a9`.
